# OpenDuet decider datasets (OpenDecider SFT + Laya System-One)

Generated by `gen_openduet.py` (seed 20261029, deterministic). 1,000 samples per domain, 4,000 total.

## Files
| File | Spec | Use |
|---|---|---|
| `system1_<domain>.jsonl`, `system1_all.jsonl` | A (System-One) | Laya training, evaluation |
| `sft_<domain>.jsonl`, `sft_all.jsonl` | B (OpenAI chat SFT) | OpenDecider fine-tuning |

Domains: `email_triage`, `skill_selection`, `safety`, `routing`.
The SFT `assistant` message is exactly the `answers` object of the matching System-One row.

## Composition (validated by validate.py)
- email_triage: 500 needs_you / 500 can_wait. Labels are calibrated noul values (about 0.90-1.00 for needs_you, 0.01-0.10 for can_wait; harder cases get less extreme values). Hard negatives: "URGENT" marketing, "no action needed", resolved incidents, "if this was you" security notices. Hard positives: terse casual pings, approvals with deadlines.
- skill_selection: 100 single-skill samples for each of the 8 skills, plus 100 multi-skill and 100 no-skill (includes near-misses like "under the weather", "shell company", "memory leak"). Every row asks all 8 noul questions.
- safety: 334 proceed / 333 needs_approval / 333 hand_off. Includes read-only commands with scary strings (`grep "rm -rf"`, `terraform plan`, `rsync -n`), and destructive actions behind innocent requests ("free up some disk space" -> `docker system prune -af --volumes`). Credentials and card data are placeholders such as `<OTP_CODE>`.
- routing: 166-167 per role across the 6 coworkers, with cross-role confusables (unit tests for invoice math -> coder, refund -> billing, changelog -> writer, OOMKilled pods -> ops).

## Caveats
1. This data is synthetic and template-driven, not extracted from the public corpora. Templates repeat structurally with varied slots. Use it as seed/eval data, and blend in real or LLM-paraphrased data before relying on it for generalization.
2. `choice` probabilities are smoothed soft labels (top class 0.90-0.99), not measured model confidence. Drop `probabilities` if you want hard labels only.
3. There is no train/eval split. Because rows share templates, split by template (or hold out a hand-written set) to avoid leakage.

## Public corpora for scaling up (not downloaded here; the sandbox has no access to these hosts)
- Email: Enron corpus (CMU, ~0.5M messages; cleaned copy on Hugging Face `corbt/enron-emails`), Avocado Research Email Collection (LDC, licensed), Apache SpamAssassin public corpus, Enron-Spam. These have no needs_you labels. Label them with a strong LLM using the same question, then audit a sample. They are also dated and skew toward corporate English, so keep the synthetic modern-notification negatives.
- Skill/tool selection: Berkeley Function Calling Leaderboard (HF `gorilla-llm/Berkeley-Function-Calling-Leaderboard`; its README says not to use `load_dataset`, use the GitHub scripts at ShishirPatil/gorilla), NexusRaven API evaluation (HF `Nexusflow/NexusRaven_API_evaluation`), ToolBench/ToolLLM, APIBench. Map each function's category to the 8 slugs, and use BFCL "irrelevance" items for the no-skill class.
- Safety: Anthropic model-written evals (github.com/anthropics/evals), AgentBench OS/DB tasks, red-team sets. Convert command traces into (request, action) pairs and label with the 3-way rubric.
- Routing: SWE-bench issues -> coder, plus public GitHub issue and Jira classification corpora -> triage/coder/ops/writer mapping.
Check each dataset's license before training, since Avocado and some others restrict use.
